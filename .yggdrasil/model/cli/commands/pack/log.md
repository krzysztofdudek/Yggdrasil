Adds the ability to install rules published by another repository. Until now every rule a repository ran had to be written in that repository: there was no way to take a body of law someone else maintains, and no way to keep taking their improvements once you had. This command does both, without a registry — a marketplace is an ordinary git repository with a manifest at its root, and the identity a package is filed under comes from the URL the user typed, so the same package published from two forks installs side by side and neither can claim the other's name.

The shape it commits to is copy-and-adapt rather than copy-and-edit. Installing copies every file verbatim and records what each one hashed to, and writes an adaptation file beside each rule; that adaptation file is the only place the installing repository writes. The reason is what an update has to be: a replacement, not a merge. A repository that edited the copy would lose the edit silently the next time the package moved, so an edit to a copy is refused outright by the gate and an update refuses to run at all while one exists, naming the files rather than discarding them.

Three refusals are deliberate and worth stating. Adding a package that is already installed is refused instead of quietly reinstalling: a second install would overwrite the copy, and someone typing it usually means the newer version, which is the other command — the one that checks the copy first and carries the adaptations across. Removing a package is refused while anything in the graph still attaches one of its rules, because removing law something still names makes every check fail on dangling names rather than on anything real. And a source that cannot be reached produces silence in the attention feed rather than an item claiming there is no newer version: an offline source knows nothing, and reporting nothing found would be a finding this run never made.

Fetching runs git through an argument array and never a shell, because a package URL and a version tag are text an attacker chooses. A failed fetch quotes at most one line of git's own output inside a sentence this command wrote, never a raw stream and never a stack — and it prefers git's fatal line over the advisory noise git prints before it, so a missing version is reported as a missing version rather than as whatever warning happened to come first.

The one thing an adopter must understand is stated in the install output rather than left to documentation: installing a package means running its author's code in this process on every check. What is fenced is what a rule may READ through the context it is handed, not the module itself.

Installing a package was supported before publishing one was, which left an author to work the shape of a package out backwards from the consuming side. Scaffolding one closes that: it writes the smallest complete package there is — a manifest, one rule that reads exactly one setting, and the pair of cases that rule needs — so the author starts from something that already passes the pre-publish check and edits it into what they meant, rather than assembling it from a document and discovering what is missing at publish time. Two details are load-bearing rather than cosmetic. The directory holding a rule's cases is drills and the first path segment of a case is what says whether it must be refused or must pass, so the scaffold writes those prefixes exactly; getting either wrong produces a corpus the runner skips in silence, which looks from the outside like a rule with no cases. And the entry it adds to the manifest is an edit to that document rather than a regeneration of it: the manifest belongs to its author and carries their comments, and rebuilding it from data would delete them without saying so. The version starts below one and the Yggdrasil it asks for is the running major rather than the exact build, since a package written against one minor works on a later one and a range naming the patch would refuse consumers for no reason at all.
