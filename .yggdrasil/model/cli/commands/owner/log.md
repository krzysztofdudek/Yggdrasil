## [2026-07-20T20:42:31.119Z]
Answering "which component owns this file" used a home-grown rule that picked the component with the longer matching path, then broke ties by name. Everywhere else in the tool that question is answered by a shared rule that puts hierarchy first: a nested component always owns a file it claims inside a parent, no matter how the two mapping patterns compare in length. The two rules agree in the ordinary case (a nested component names a specific, longer path), but they disagree when a nested component is configured to cover a broader set than its parent — and there this surface reported the parent while the file was actually verified under the nested component. It now defers the ownership decision to that one shared rule, so what this reports always matches the component whose rules actually apply, and keeps its own presentation of how the file matched.
