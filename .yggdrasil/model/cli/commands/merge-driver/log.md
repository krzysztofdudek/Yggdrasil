## [2026-09-27T21:01:40.277Z]
Parallel branches collided on the same few files at nearly every merge — a node log both sides appended to, a lock both sides recorded verdicts in — and each collision was resolved by hand or by taking one side whole. Git can resolve them itself through a merge driver, but a driver is a function of one file handed to a program, and it fails silently in three ways: a driver that exits 0 without writing makes a clean merge of the wrong content, a driver configured whose program is gone leaves the file conflicted with ours alone and no markers, and a driver named but never defined falls back to plain markers. So the command always writes its result before a clean exit, writes markers and exits 1 when it refuses, and on anything unexpected hands the file to git merge-file with markers rather than leaving ours as if it were the answer. It reads no graph and writes no lock, because the file is all a driver is given.
## [2026-09-27T22:25:00.980Z]
The merge-driver command is new: git runs it for every log.md and every committed lock file, merging a log as the verified union both sides agree on and a lock per key, and refusing with conflict markers wherever the reconciliation would refuse, so parallel branches stop colliding on the same few files at every merge. It arrived in one batch with the coverage and verdict-vocabulary work.
## [2026-09-27T22:32:41.153Z]
An unexpected failure inside the driver, such as a side git handed over that cannot be read, used to fall back to git's text merge and exit 1 with the cause only in the debug log, so the person merging saw a conflicted file and no reason. It still writes git's markers first, then aborts through the shared unexpected-error path, which puts the cause on stderr and exits 1; the driver is tested through its registered command rather than through an exported internal.
