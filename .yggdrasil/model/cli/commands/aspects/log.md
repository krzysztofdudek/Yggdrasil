## [2026-07-10T09:59:33.876Z]
Added an at-a-glance health view to the aspect listing so a maintainer can see, per rule, how broadly it applies and whether its recorded results still match the current code — without paying for a full review. The guiding intent is honesty about what has actually been checked: when a rule's units have no valid result on record — never checked, or checked and since gone stale — the view must show them as not-yet-checked, never as a clean zero. Reporting an unchecked rule as passing is exactly the false confidence this view exists to prevent. Waivers that silence every rule at once are summarized on their own line rather than blamed on any single rule, since attributing a silence-everything waiver to one rule would misstate where the risk sits. The view is strictly read-only: it inspects existing state, records nothing, and calls no reviewer, so looking at rule health can never itself change a result.
## [2026-07-10T18:11:56.973Z]
Fixed a subject-verb agreement bug in the per-rule health summary's wildcard-waiver note. The sentence conjugated the noun (marker/markers) and the copula (is/are) to the waiver count but left the intervening verb hard-coded as "apply", so the single-waiver case rendered "1 wildcard suppress marker apply ... and is not counted" — a grammatical error in a message adopters read directly. The verb is now conjugated with the count too ("applies" when one, "apply" when many). This is user-facing wording polish only; it changes no counting, no data, and no exit behavior. A unit assertion now pins both the singular ("applies") and plural ("apply") renderings so the disagreement cannot silently return.

## [2026-07-11T18:56:07.319Z]

## [2026-07-12T16:10:53.762Z]
The per-rule health view now shows how often a rule has actually caught a violation against how often it was exercised, distinguishing a genuine exercise from a cached re-render and never pooling the two reviewer kinds whose false-positive mechanisms differ. ## [2026-07-13T22:29:18.961Z]
The rule-health view gained a false-block signal: a per-rule count of how often that rule's refusals were LATER waived or overturned by a human — an honest read of a rule that may be blocking wrongly, so a maintainer can spot and retire the worst offenders. It joins the recorded verification-event history (past refusals) against a live scan of suppress waivers: a refusal is a false block when a waiver for the same rule now covers the refused unit, distinguishing a still-refused block a human waived from one that was re-approved after a waiver moved.
