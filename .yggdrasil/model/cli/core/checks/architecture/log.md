## [2026-05-29T22:21:12.650Z]
The graph validation checks were extracted from a single oversized validator module into domain-grouped modules (architecture, aspects, mapping and coverage, relations and flows) plus a small shared helper, leaving the orchestrator that runs every check and assembles the result in place to compose them. The move was verbatim: no change to which rules run, their order, their diagnostic messages, or their verdicts. The motivation is that one very large source file degrades reviewer accuracy and risks context-window truncation that can spuriously reject unchanged code; keeping each unit small enough to be reviewed in full removes that failure mode.
## [2026-05-30T10:05:16.257Z]
Port contracts are now enforced uniformly across every relation type. Previously the contract validation exempted event-based relations, while the rule-propagation that carries a port's required rules onto a consumer did not — so an event relation to a component that exposes ports could receive the port's rules without ever being required to declare which port it consumes. That exemption was removed: any relation to a port-bearing target must declare its consumed ports, matching how the rules already propagate and what the schema already states.
## [2026-06-08T16:40:57.262Z]
The check that every mapped file satisfies its node type classification predicate now expands a glob mapping entry to the files it matches and checks each, instead of evaluating the literal pattern string. Evaluating the string produced false wrong-type errors for a glob whose matched files were valid but whose pattern text did not itself satisfy the predicate (for example a pattern without a file extension under a predicate that requires one). Exact-file and directory entries are checked as before.
## [2026-06-13T10:52:15.802Z]
Port and relation validation errors put a bare location label (the relation source and target) in the what-happened line and hid the actual problem in the why line, so an agent scanning the headline learned nothing went wrong. Each headline now states the problem directly (forbidden relation, undefined required aspect on a port, missing consumes, target without ports, disallowed parent type), with the relation kept as context; the why line was trimmed to the consequence and the allowed-set hint.

Every diagnostic emitted by the architecture validators now carries an explicit what/why/next message structure at its call site, so the agent always sees the problem, why it matters, and the remedy uniformly across all architecture checks rather than only the few that spelled it out before.
## [2026-06-19T11:07:37.310Z]
The enforce-strict architecture diagnostic now points the reader at the built-in schemas command for the architecture field reference, instead of a per-project schema file path. Reason: that file is no longer part of a project; the reference is embedded in the tool and read through a command.
## [2026-06-27T07:04:48.889Z]
The relation validator now enforces three new architecture policies that were previously unhandled: (1) a per-type default policy — when a node type declares relations.default: deny, any relation type not explicitly listed is forbidden, so the type acts as a sink; (2) an explicit empty target list means "deny all targets for that relation type", where previously an empty list was dropped at parse time and silently treated as allow-all; and (3) the wildcard target sentinel (["*"]) in an explicit list allows any target type for that relation, which is useful for types that use default: deny but need to selectively open one relation type. The fast path was also corrected: the old guard that skipped the entire node when typeConfig.relations was falsy would silently skip nodes whose type had default: deny but no explicit per-type lists, allowing forbidden relations to pass unchecked.
## [2026-07-03T08:25:54.200Z]
A node type's when predicate must classify a directory-form mapping entry by the files it owns, not by the literal directory string. A directory entry such as src/emails/ and the equivalent extension glob src/emails/star-star/star.ts describe identical ownership and are both documented-valid mapping forms, so type classification must treat them identically. Previously a directory entry was matched literally against an extension-glob when, which never matches a bare directory name, producing a spurious type mismatch for the most natural first mapping a user writes. The fix expands every mapping entry to its concrete owned files through the same helper the mapping and coverage layer uses, so classification matches ownership exactly. A non-glob entry that resolves to no file on disk is still evaluated as-is, so a content predicate over a missing file still reports that the file cannot be read, while an empty glob stays reported by the mapping-existence check.
## [2026-07-15T08:27:06.702Z]
Adds an architecture-integrity check that every target-type name listed in a relation allow-list is a defined node type or the any-target wildcard. This is the relation-side counterpart of the existing undefined-parent check: a typo in an allow-list target was previously silent, so a node of the intended type never matched the misspelled entry and the relation was either over-restricted or the constraint never fired as meant. Catching the dangling name before any node is judged keeps the vocabulary self-consistent.
