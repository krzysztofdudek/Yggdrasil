The motivation is that the reviewer concatenates all of a node's files into each aspect prompt, so an oversized node risks exceeding the model's context window, which deterministically rejects unchanged code near the truncation point; a file-count limit missed this because one very large file could stay under the count while still blowing the prompt. Binary files do not count toward the budget, and a node mapping a single unsplittable generated or binary artifact (a lockfile, an append-only changelog, an image) may carry a documented per-node exemption with a required justification.

## [2026-07-19T10:07:18.444Z]
The gitignored-mapping validator builds its tracked-file set from the repository file walk and flags any mapped file absent from that set as excluded by .gitignore. But the walk skips the graph directory itself for structural reasons (it holds the graph and its rebuildable state, not reviewable source), so committed rule files living there are structurally absent from the set — not gitignored. Mapping such a rule file by its literal path is sanctioned meta-modeling: the graph bringing its own rule sources under a node so they are verified like any other code. Treating their structural absence as a gitignore exclusion made the check refuse the exact mapping the guidance tells authors to write, and it did so inconsistently — a glob or directory form slipped through only as a side effect of the existence probe failing on a non-literal path, while a plain file path was blocked. The fix exempts structurally-excluded paths from this check using the same predicate that already distinguishes structural exclusion from gitignore exclusion elsewhere, so a literal graph-directory mapping is accepted while a genuinely gitignored source file is still refused.

Two ownership and coverage fixes in the mapping validators.

It now resolves ownership through the canonical child-wins resolver so coverage attribution matches the subject set that is actually verified.
