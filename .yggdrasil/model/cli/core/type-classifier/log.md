## [2026-08-02T11:51:51.127Z]
The classification cache key now folds in the file's own repository-relative path and hashes raw, un-normalized bytes instead of the line-ending-normalized hash used for verdict hashing elsewhere, so classifyFile's cache lookup and write both take the path alongside the content hash. Two files with identical bytes at different paths, or one file whose line-ending style changes at a fixed path, previously could share or fail to invalidate a cache entry; neither can now.
## [2026-08-02T13:43:54.970Z]
classifyFile now returns its matches array sorted by type id, both when freshly evaluated and when read back from a cache hit, instead of leaving it in whatever order the architecture file happens to declare its classifying types or a cache shard happens to have stored them. The match SET was already order-independent — the classification cache's own architecture-predicate hash already sorts by id before hashing — but several callers render the ARRAY itself verbatim: the ambiguous-node-type message naming every overlapping type, and which type a strict-claimed file is named under. So the identical failure could read differently purely from whether an answer came from a warm cache entry or a fresh evaluation, triggered by nothing more than a harmless reorder of unrelated type declarations elsewhere in the architecture file. Sorting once, at the single point every caller's answer already passes through, makes the rendered order canonical regardless of cache state or declaration order.
## [2026-08-02T14:47:29.847Z]
closest and unreadable, the other two arrays classifyFile returns, are now sorted the same way matches already was: closest by score descending then type id ascending (composed BEFORE the top-3 slice, since declaration order could otherwise decide which candidates even made the cut once ties reached beyond three, not merely their sequence), unreadable by type id alone. The earlier entry describing the matches sort said sorting one array "makes the rendered order canonical regardless of cache state or declaration order" — true only of matches at the time; closest and unreadable still diverged between a warm and a cold run for a pure type-declaration reorder, and closest could even name a different set of candidate types, not just reorder the same ones. All three of classifyFile's returned arrays are canonical now: the cache's stored shape has exactly five fields, two of them bookkeeping that is never rendered and the other three exactly these arrays, so a pure whole-block reorder can no longer change what any caller renders regardless of which path produced the answer.
