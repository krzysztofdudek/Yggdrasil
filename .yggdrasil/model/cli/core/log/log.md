## [2026-07-20T04:43:32.109Z]
Two fixes to keep log entries and their boundaries intact.

Adding an entry must reject a justification that contains an unclosed code fence. Because entry headers are recognized by a line pattern, an unterminated fence in one entry would swallow every following entry header into that entry's body for later readers, silently destroying the boundaries between entries. Such a justification is now refused up front with guidance to close or remove the fence.

Reconciling a log after a merge must detect real version-control conflict markers without firing on ordinary Markdown. The check previously also treated a line that is a run of equals signs as a conflict marker, but in Markdown such a line is a legitimate heading underline or horizontal rule, so a normal log could be misread as conflicted. Detection now keys only on the unambiguous opening and closing conflict markers, which a genuine conflict always emits, so no real conflict goes undetected and no ordinary log is falsely flagged.
## [2026-09-06T22:01:42.516Z]
A rule can now keep a log of its own beside its source, for the same reason a component keeps one: what a rule is measured against changes over time, and the reason behind a change belongs where the next reader of the rule will look rather than in whichever commit happened to carry it. A clone has the log; an archaeology dig through history does not scale to a rule somebody meets for the first time. Nothing parses that log as part of the graph and it is never a verdict input, so recording why a case was taken in invalidates nothing — exactly as a component's log does not. The composition of an entry moved into one place shared by both kinds of log: the entry shape that every reader splits on, the two refusals that stop a body from destroying that boundary for everything written after it, and the rule that a new entry never carries a timestamp at or before the one before it. Two implementations of that would have been two sets of the same bug, and the failure mode is silent — a reader simply stops seeing entries.
## [2026-09-07T08:00:36.013Z]
A rule's standing — draft enforces nothing, advisory reports, enforced refuses — is the whole of its authority, and until now moving one left no trace anywhere a reader of the rule would look. Two halves close that here. A change recorded through the tool is written into the rule's own history in one fixed sentence: where it moved from, where to, who decided, and on what evidence. And the standing each rule was last seen at is remembered, so a change made by hand shows up as a difference from that memory and is written down exactly once — not never, and not again on every later run. The sentence is deliberately a sentence rather than a metadata block: a person reads it as prose, a later run reads back the part it needs from inside it, and the log stays a thing people actually read. Two rules keep the record honest. What a caller records is checked against the rule's file first, because a history that claims a change nobody made is worse than no history. And a change the caller already recorded advances the memory silently instead of being said a second time, which is decided by reading the rule's own log rather than by trusting a flag — so the two paths agree even when they run days apart.

merge-resolve rejected the union it had just written whenever one side of the merge ended its log without a final newline. Writing the union has to give that side's last entry a newline once other entries follow it, but the verification in the same run compared the entry against the side's original bytes, saw the one extra byte as an altered body, and refused with missing or has altered 1 entry, leaving the adopter with a correct file and a red command. ## [2026-09-24T02:30:17.946Z]
merge-resolve now understands a rebase or a cherry-pick stopped on a conflicted log, not only a merge. Before, it knew only a merge in progress, so at a rebase stop it refused with "HEAD is not a merge commit" even though yg check named it as the fix, and people kept one side and re-added the other side's entries with fresh timestamps, which destroys the dated, append-only history the log exists to keep. The replayed commit contributes only the entries it added over its own parent, not everything since the merge base: a cherry-pick carries one commit's change, and a rebase replays one commit at a time, so taking the merge base would resurrect entries of commits that were dropped or never picked. HEAD's log stays whole and in its order, and each added entry lands where its timestamp falls, so the result passes the append-only and date-order checks after the operation continues. A replayed commit that dropped or changed an entry its parent had is refused, because a union can carry added entries but not a rewrite. A rebase counts as in progress only while its state directory exists, so a REBASE_HEAD a finished rebase left behind is not mistaken for one.
## [2026-09-24T08:19:00.941Z]
Resolving a conflicted log took the shared history from the log at the git merge base and required both sides to start with it byte for byte. A merge written in date order puts an older entry from the other branch ahead of newer ones of the branch's own, so afterwards the branch's log no longer starts with the log at any later merge base, and the next merge from a branch cut before that reorder was refused as a rewrite although nothing had been rewritten; three consecutive merges of one release line hit it, the last with no way through. The shared history is now what the two sides' logs themselves start with, their longest run of identical leading entries, and the union is that run byte for byte followed by every entry either side holds after it, each once, in date order with ours first on a tie. Verification accepts exactly that union. The merge base keeps one job, a sanity check that neither side lost or changed an entry the base had, compared by presence rather than order; two different entries at one datetime are refused as a rewrite. Entries are now deduplicated with a side's missing final newline restored, so an entry carried by both sides appears once. Rebase and cherry-pick stops already compared entries by content and stay as they were.
