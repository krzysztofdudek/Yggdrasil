New pure helper module implementing the coverage-tier partitioning algorithm for the coverage-modes feature. The three exported functions — normalizeRoot (strips slashes, maps / to empty string for whole-repo matching), matchesRoot (prefix-safe directory matching), and partitionByCoverageTier (longest-match-wins, excluded wins equal-length ties) — encode the core invariant that the default CoverageConfig of { required: ['/'], excluded: [] } must behave identically to the pre-existing whole-repo required-coverage behaviour. These functions are pure (no I/O, no side effects) and are re-exported by check.ts so existing callers are unaffected. The module is isolated here so check.ts stays within the 40,000-character reviewer budget.

## [2026-07-24T14:33:21.883Z]
The coverage module now answers one question for a caller outside the check itself: given a set of paths, which of them would the gate report as blocking unmapped-file errors under this project's coverage settings? It is asked right after setup writes the agent-rules files into a project's root, so an adopter upgrading from an older release learns in that moment that a project requiring its whole tree will now fail on them, and how to settle it.

The prediction lives here, beside the tier partitioning it depends on, rather than in the command that asks: it must be computed from the same two primitives the gate itself uses — is the path covered by any component's file list, and which tier does it fall into — so a caller cannot approximate the rule with its own copy and then disagree with the gate it is predicting. That divergence is the failure mode worth designing against: a warning that fires when the build would be green, or stays silent when it would be red, is worse than no warning at all.
