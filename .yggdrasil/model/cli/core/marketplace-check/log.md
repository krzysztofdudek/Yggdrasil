## [2026-09-10T17:16:44.783Z]
A package is copied verbatim into other people's repositories and runs its author's code there on every check, so the faults worth catching are the ones that are invisible from inside the repository that wrote it. Five questions, chosen and no more: whether the two manifests agree with the directories that are actually there, whether every rule loads under the very loader a consumer will load it with, whether every bundling rule stays inside its own package, whether every setting a rule reads is declared and every setting declared is read, and whether the package will still mean the same thing somewhere it has never seen. That last one is the reason the whole thing exists. A review date, a reference path, a named reviewer tier and a scope glob anchored to a literal directory all mean something precise in the author's repository and something else, or nothing at all, in everybody else's, and a rule that quietly matches nothing after installation is worse than one that refuses loudly. The settings question is answered from the text of the rule rather than by running it, and answers conservatively: an access that cannot be resolved to a literal name is reported as an incomplete reading rather than guessed at, which is what makes it safe for a setting read and never declared to be a refusal while a setting declared and never read stays a warning and falls silent entirely once the reading is known to be incomplete. Presence of a rule's proof cases is checked and the cases are not run, because running one needs the context a rule is handed and there is deliberately nothing here to build it from. The credential scan is a heuristic and is called one everywhere it appears: it earns its place on asymmetry rather than completeness, since a credential that gets through here spreads to everyone who installs the package, which is also why one inside a comment counts and why the refusal names the file and the line and never repeats the finding, that sentence being destined for build logs. The error codes live with the checks that emit them rather than in the shared registry the enforcement gate groups and tallies, because this runs in a different repository, on a different document, outside that pipeline entirely.

Every filesystem path this surface prints now reads the same way on every platform. A refusal naming a directory, and the line that says which repository was checked, previously carried whatever separator the host uses, so the same repository produced two different sentences depending on who ran the command — which makes an assertion, a diff of two build logs, or a support conversation quoting one of them harder than it needs to be. The paths are also what a reader copies back into a command, and one form works everywhere.
## [2026-09-10T17:53:22.732Z]
The heuristic credential scan is gone. It was built and then cut: matching shapes that look like API keys across every file a package ships is a different kind of promise from the other four questions here, which are all answered exactly — a manifest either matches the directories or it does not, a rule either loads or it does not. A pattern scan is never finished, and its result is a floor rather than a clearance, so it would have been the one answer in this command that a reader could not take at face value. Package files are still opened and an unreadable one is still refused by name, because a file that cannot be read cannot be copied into whoever installs it; what has gone is looking at their contents for anything in particular.
