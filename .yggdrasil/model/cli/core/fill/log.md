## [2026-07-03T06:25:31.672Z]
A malformed suppression marker (one missing its required reason) in a mapped source file is now reported as its own distinct disposition at fill time, separate from a rule-checker runtime error. Previously such a marker — a fault in the source file text, not in any checker — was funneled through the same path as a crashed checker and rendered with a message telling the author to fix the checker, which is misleading because the checker is correct and never ran a judgment. ## [2026-07-05T13:25:13.359Z]
Refusals and infrastructure failures encountered during automated verification runs have been effectively invisible once a run finishes: a refused pair renders in the terminal output for that one invocation and then either gets fixed or sits cached in the lock, and an infrastructure failure (a reviewer that could not be reached, a check that crashed) looks identical after the fact to a pair that simply was never touched. There was no durable, cross-run trail of what actually happened during each verification attempt. Every completed verification attempt now appends one local, best-effort record describing its outcome — approved, refused, or one of the specific no-write failure modes — to a file that lives entirely outside the committed graph and is never consulted by any verification logic. This keeps a running history of rule behavior over time (which rules refuse repeatedly, which infrastructure paths fail often) available for later analysis without letting that history influence, or be influenced by, the enforcement decisions themselves — the record is written strictly after the authoritative decision is already final, and a failure to write the record can never change or block that decision.
## [2026-07-05T14:33:33.657Z]
The fill stage now records, for each LLM verdict produced under multi-vote consensus, how the individual votes split (how many favored the recorded outcome versus the total cast) as part of the same local telemetry line already written per verdict. Previously only the aggregate approved/refused disposition was recorded, so a narrow majority and a unanimous vote looked identical after the fact. ## [2026-07-06T14:14:59.509Z]
Deterministic checks now run across a worker-thread pool during the approve fill, instead of one after another on a single core. These checks are dominated by source parsing (a CPU cost), so serial execution bottlenecked the free deterministic gate — the exact path CI and pre-commit run — on one core regardless of how many the machine has. The number of threads is received as an explicit parameter rather than read from the environment here, so this stage introduces no dependence on machine state that could vary a result; the thread count changes only wall-clock, never a verdict, and defaults to a single in-process worker when unset so the sequential behavior is the degenerate case. Each check still runs the identical rule against the identical inputs; results are lowered to plain data across the thread boundary and a structural error is rebuilt on the receiving side so failure handling (a malformed waiver marker, a re-run on an inconsistent read) is unchanged. A crashed worker fails closed — its unit is left unverified and a replacement is spawned so the rest of the queue keeps its parallelism.
## [2026-07-06T18:21:57.202Z]
Refined the deterministic worker-thread pool so it engages only when there is enough work to justify itself. Each worker pays a one-time parser/WASM warmup cost, so spawning threads for a tiny fill set is strictly slower than a single warmed in-process parser — and slow enough, on a constrained or contended machine, to blow a tight subprocess time budget. The pool now sizes itself so every worker receives a minimum number of pairs before it is created; below that, the phase runs in-process. This changes only wall-clock, never a verdict: the same check runs on the same inputs either way.
