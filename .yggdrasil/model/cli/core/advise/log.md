Hardened the freshness coupling behind the "a tight file family shares no rule of its own" proposal so the only natural reconciliation is the complete one.

Those proposals are read from an offline miner's output file, which carries its own format version and is validated against a separate live code-analysis shard schema. A build-time coupling anchors the two: if the live shard schema advances past the anchor, the build goes red until a human re-validates the miner.

The gap closed: when the live shard schema later moves, that coupling could be re-satisfied by bumping ONLY the anchor constant while leaving the accepted file-version gate unchanged. A candidates file produced under the OLD schema would then still parse and be surfaced to a human as a live rule-family proposal, even though the analysis it rests on no longer reflects the current schema. A stale proposal presented as live could push someone toward creating a rule from analysis that no longer holds.

The fix requires bumping BOTH the anchor AND the accepted file-version gate in lockstep (and having the miner emit the new file version) whenever the shard schema moves, so an old-version file is rejected at parse rather than rendered as fresh. The accepted file-version gate is what actually rejects the stale file; the build-time coupling only guards the anchor. This was made self-documenting via the coupling guard's failure message and the two constants' doc-comments, and the accepted-version constant was exported so the guard can be asserted against the real value rather than a duplicated literal.

No runtime behavior or on-disk data shape changed: the file version, the candidates-file layout, and the producer/consumer field contract are all untouched. This is purely a stronger, self-documenting reconciliation guard.
