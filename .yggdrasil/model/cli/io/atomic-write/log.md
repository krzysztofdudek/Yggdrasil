## [2026-07-03T13:26:51.001Z]
The temp file used for the write-then-rename is now unique per writer (process id, a process-local counter, and random bytes) instead of a fixed name derived from the target. A fixed temp name raced whenever two writers targeted the same file — a parallel test worker or a second CLI run writing the same shared AST-fact cache shard or lock — because one writer's cleanup or rename pulled the temp out from under another, surfacing as a spurious file-not-found on rename over a byte-clean tree. With a private temp per write, only the final rename onto the shared target is contended, and rename is atomic, so a reader always sees a complete old-or-new file. Every caller writes content that is either content-deterministic or single-owner, so last-write-wins on the target is correct. The previous stale-orphan pre-removal is dropped as unnecessary under unique names.
## [2026-08-07T11:02:55.064Z]
An atomic write leaves a temp file beside its target between writing and renaming, and cleans it up when the write throws. Nothing runs when the process is killed outright — an out-of-memory abort, a forced kill, a machine losing power — so the temp survived and read as something the tool had meant to leave behind. A sweep now removes such leftovers, scoped narrowly enough that it can only ever match this module's own temp naming, only in the directory it is pointed at, and only once a leftover is old enough that no concurrent writer could still be mid-write on it. Best-effort throughout: a sweep that cannot read the directory or loses a race says so in the debug log and gives up.
