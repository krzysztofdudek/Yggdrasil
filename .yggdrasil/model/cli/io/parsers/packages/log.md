## [2026-09-10T15:24:52.926Z]
Introduces reading the three documents a repository needs in order to run law published somewhere else: a marketplace's manifest of what it publishes, a package's own manifest, and the consuming repository's record of what it copied in. Two decisions here are worth keeping. First, absence means different things for different documents: the two manifests are expected — the caller named the directory they must be in — so a missing one is refused by name, while a missing record simply means no packages are installed, because almost every repository has none and making them all carry an empty file would be ceremony. A record that IS present but unreadable is refused loudly instead, since reading it as 'nothing installed' would silently stop checking every copied rule in the repository. Second, whether the running build is new enough for a package is asked only when a package is being brought in, never while a graph is being loaded: judging it at load time would strand an already-installed package as unloadable after an upgrade, and therefore un-removable, which is the worst possible moment to refuse. A package directory is also checked in both directions against what its manifest declares — a declared rule that is not there would install as law that can never run, and a rule directory that is there but undeclared would arrive as law nobody announced.

Issue codes are public names: adopters, CI scripts and sibling tools branch on them, and the reference pages explain them. They used to be free string literals, so a code could be emitted that no page explained, or documented while nothing emitted it. Every code is now a member of one typed vocabulary, and every type that carries a code is typed with it, so an unregistered or misspelled code fails the typecheck instead of shipping.
