## [2026-09-10T15:24:53.493Z]
A rule installed from another repository is copied in verbatim and never edited, so everything the installing repository wants different is written in a separate file beside the copy and merged over the rule's own definition here, before any of it is validated. Merging before validation rather than patching the result afterwards is what makes an adapted value indistinguishable from one the rule declared itself: every check downstream, and every message it can produce, sees exactly one definition. Three choices behind the merge. Lists replace rather than combine, because a list that combined could never be shortened — a repository could add a reference but never drop one the package shipped. Maps merge key by key, because the field anyone actually wants to change about a reviewer is its tier, and whole-map replacement would force them to restate the reviewer's kind, which is not theirs to state: it is fixed by which rule file the package ships. And the adaptation file refuses an unrecognised key even though a rule's own file tolerates one — a deliberate asymmetry, because the two are written under different conditions. A rule's file is authored once by whoever wrote the rule, and tolerating a key from a newer build is what lets one rule work across versions; an adaptation is written by someone tuning a rule they did not write, where a misspelled key reads as a change that was applied when it was silently dropped. A rule may also now name its companion resolver by path instead of shipping one beside itself, which is how a rule from a package can use a resolver written here — the package cannot know this repository's layout. Its bytes join the rule's own files under the name the rest of the system looks for, so editing that resolver invalidates the verdicts it helped produce, exactly as editing a packaged one would.
