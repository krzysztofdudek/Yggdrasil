## [2026-05-30T18:08:10.281Z]
The vocabulary for how a rule is verified was reduced from three kinds to two. Previously a rule was checked by one of: a human-language reviewer, a single-file programmatic check, or a graph-aware programmatic check. The two programmatic kinds are now a single "deterministic" kind, leaving just deterministic-or-reviewer.

The motivation: the three-way split was drawn on the wrong axis. It described HOW a programmatic check reached its context (one file at a time, versus the whole graph), but the distinction that actually matters to a rule author and to cost is whether verification is local-and-free or requires the paid, non-deterministic reviewer. The single-file kind was already a strict subset of the graph-aware kind — every input the former could see, the latter also provides — so maintaining two of them forced rule authors to make a false choice up front and forced the engine to carry two parallel handling paths for one concept. Collapsing them removes that false choice and the duplicated handling, and routes every programmatic check through the one graph-aware path.

The language a programmatic check infers for a source file is determined solely from that file's extension, so a check no longer declares which languages it targets. A rule's verification kind being deterministic is also no longer carried as a separate synthetic identity signal — a deterministic rule's identity is fully covered by the files it already tracks — which keeps re-verification of such rules free.

The canonical drift hash must be identical across machines regardless of the operating system or runtime locale: it is the value that decides whether a baseline still matches the code, and a baseline computed on one machine is read and compared on another. The file-digest ordering that feeds this hash therefore uses a code-unit (byte-order) comparison rather than a locale-aware one. Code-unit ordering is locale-independent and matches how the typed identity portion of the same hash is already serialized, so both halves of the hash are ordered consistently.

## [2026-07-31T08:25:43.697Z]
The nested-project boundary (a subtree carrying its own .yggdrasil/ graph, or its own .git checkout/submodule/worktree) is now derived by walking the real filesystem instead of scanning whatever candidate file list a caller happened to already have. The old approach inferred the boundary from paths already present in a list, so a glob mapping filtered by extension, or a .gitignore line hiding just the marker, could never surface it and the boundary silently failed to apply. The new filesystem walk is cached once per process so repeated lookups against the same project root stay cheap; a directory/glob mapping's own file listing also now skips a .git entry it encounters directly, matching the coverage walk's existing behavior.

## [2026-07-31T10:21:16.087Z]
The .git marker required only presence, not real content, so an empty .git/ directory or a .git file with garbage or missing content silently drew a nested-project boundary the .yggdrasil marker already refused to draw under the identical condition. Both forms of the .git marker now require the same real content .yggdrasil already required: the directory must contain a file somewhere inside it, and the file must parse as a real gitdir pointer.
## [2026-07-31T12:04:32.475Z]
An excluded path was only ever kept out of the enforcement surface when it sat inside a nested project's own filesystem boundary; an adopter's own coverage.excluded config had no effect on a node's mapped files at all, so excluding a vendored subdirectory from coverage changed nothing about what got reviewed or billed. The nested-project boundary and the adopter's config are now packaged as one exclusion set with a single predicate every caller asks, so a path excluded either way is dropped everywhere consistently, and mapping expansion itself now honors both sources rather than only the filesystem-derived one.
## [2026-07-31T14:13:50.856Z]
Added a predicate that names which of the two independent sources -- a nested project's own boundary, or an adopter's own coverage.excluded config -- actually caused a given path's exclusion, so a caller that already knows a path is excluded can say why instead of listing both possible causes. Also added a helper that counts, for a set of coverage-visible files, how many a node's mapping textually covers but an exclusion removes from enforcement anyway, so a summary counter elsewhere can report those files under the honest term instead of folding them into ownership they do not actually have.
## [2026-07-31T20:55:11.679Z]
The exclusion-source lookup gained a companion helper that renders which of the two exclusion sources (a nested project's own boundary, or a coverage.excluded root) applies as the same clause every exclusion message in the graph already uses, so a caller reporting an excluded path no longer hand-rolls its own phrasing of the same fact. The structure-aspect read guard's own thrown error also now carries which source applied, determined once at the point the read is rejected, instead of leaving every consumer of that error to tell an excluded path apart from a genuinely undeclared one on its own.
