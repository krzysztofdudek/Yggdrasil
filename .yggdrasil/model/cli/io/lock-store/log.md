## [2026-06-12T11:45:55.506Z]
Conflict-marker detection in readLock was changed from a substring check (raw.includes('<<<<<<<')) to a line-anchored regex (/^<<<<<<< /m.test(raw)). The motivation: verdict reason strings may legitimately contain the text '<<<<<<< HEAD' when a reviewer quotes merge-conflict fragments from the source being checked. A substring match would throw LockInvalidError on a valid, self-written lock file in that case. The line-anchored form matches only real git conflict markers, which always start a line and are immediately followed by a space — a JSON-escaped string value inside the file cannot satisfy this pattern. The behavioral guarantee is unchanged for actual conflict-markered files: a file with a real unresolved merge conflict still throws.

The committed verdict lock no longer carries any relation-conformance results. The architecture relation check that verifies every code dependency is declared was moved from a cached verdict to a value computed fresh on every run, so persisting its outcome in the lock would be storing a result that is always recomputed anyway and could go stale against the code. ## [2026-06-20T11:18:08.118Z]
Split verdict-lock storage from one file into a committed/gitignored triad. WHY: deterministic-check verdicts are a pure local performance cache — committing them added roughly half the lock's bytes and merge noise while a fresh clone can recompute them for free with no key and no model call. The store now reads three files into one unified lock and, on write, partitions verdicts by aspect KIND (deterministic vs LLM) rather than by any per-entry field: an LLM aspect that ships a companion hook also records out-of-subject observations on its entry, so kind is the only safe discriminator. Deterministic verdicts go to the gitignored cache; LLM verdicts and the per-node log/closure baseline stay committed in two separate files so log churn never mixes with verdict churn. A scoped write mode lets a deterministic-only run touch ONLY the gitignored cache, so a CI run produces zero churn in committed files.
