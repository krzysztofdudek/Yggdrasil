## [2026-07-31T17:59:32.846Z]
An import specifier resolved fresh from source can name any file on disk, including one this graph excludes — a coverage.excluded root, or a nested project's own boundary. The owner index that turns such a resolved file into a node must answer 'no owner' for an excluded file the same way every other ownership question in this graph already does, or an import reaching into an excluded subtree keeps naming its textual owner and wrongly trips the undeclared-dependency check. The Go and Java package resolvers go one step further: given a package/wildcard import, they pick a representative file for the whole directory by consulting an owner index too, so they can attribute the import to that file's owner. That picking index needs the identical guard, or it can land on the one excluded file in an otherwise ordinary package and silently drop an edge that is legitimately reachable through the package's other, non-excluded files — the opposite failure from leaking an excluded file's own ownership, and just as wrong. Every caller that resolves a specifier fresh from source now builds its owner index through one shared, exclusion-guarded constructor, so the index that decides a resolved file's node and the index that arbitrates a package's representative can never drift apart on what counts as excluded.
