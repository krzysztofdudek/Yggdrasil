## [2026-06-29T05:24:52.926Z]
Introduced a single read-only gateway between the read-only audit portal and the engine. Previously the portal pipeline declared direct dependencies on a dozen separate engine subsystems — graph loading, the check runner, lock verification, pair computation, the relation analyzer, the suppression scanner, issue grouping, the effective-aspect cascade, reviewer-tier selection, and the log reader. That spider of edges meant any change to an internal subsystem could ripple into the portal, and there was no single place that guaranteed the portal stays read-only. This module is now the ONE place the portal reaches the engine: it wraps every needed call behind a clean read-only surface, loads the graph committed-only so secrets are structurally unreachable, and imports no lock writer. Concentrating the coupling here lets the read-only invariants (no secrets, no lock writer, committed-only load) be enforced mechanically on this one node, and lets the rest of the portal depend on just this facade plus the data contract.
## [2026-06-29T12:36:31.021Z]
Added three read-only provenance/freshness functions to the single engine seam: a content hash over the committed lock triad (nondeterministic verdicts + per-node logs baseline; the gitignored deterministic cache is excluded so the hash is stable across machines for one commit), a git HEAD commit-ref reader that follows .git/HEAD to its loose or packed ref and reports nothing rather than a fabricated ref outside a git tree, and a per-node source-freshness comparison against the committed fingerprint baseline. Freshness fires only where a committed baseline exists, because the engine records a source fingerprint only for log-required node types; a missing baseline is the normal case and must never be read as a change, so the portal cannot paint the whole repo unverified from absent baselines. The two cases a missing baseline leaves uncovered are already honest elsewhere — a node with reviewer pairs flips them to unverified on any input change, and an unguarded node is already its own distinct non-green state — so this signal adds exactly the one remaining case: a node whose green attests specific committed bytes that have since been edited.

The shared suppression scan used by both the audit command and the live portal inventory now treats any mapped node source as an eligible waiver site regardless of file extension. The prose and documentation exclusion is scoped to unmapped files only, because the enforcement path honors a real marker in any mapped file — including mapped documentation or a meta-model document — so excluding such files by extension would let a live waiver be honored yet stay invisible to the inventory. Both callers now derive the mapped-source set from the graph and pass it into the scan, so the honoring path and the audit path agree on where a waiver can live and no file can be a live waiver site while being absent from the inventory.
## [2026-07-03T07:33:08.389Z]
The shared file-eligibility rule that decides which files can hold a honored suppression waiver — and therefore which files the audit inventory must list — was moved into its own focused unit, separate from the suppression-scan logic. Bringing the honoring path and the audit path onto one eligibility rule had grown the scan file past its focused-size boundary; splitting the rule out keeps each file to a single responsibility while preserving the invariant that no file can be a live waiver site while being invisible to the suppressions inventory.
## [2026-07-05T08:55:06.870Z]
The git commit-ref reader assumed .git is always a plain directory under the repo root. A linked development worktree checks out the repository with .git as a one-line pointer file to a private per-worktree git directory (which itself points back to the main repository's shared refs), so the reader silently found nothing and reported no commit ref at all whenever verification ran from such a worktree. The reader now recognizes the pointer-file form, follows it to the private git directory for the worktree's own HEAD, and follows that directory's pointer back to the shared location for branch refs, so the reported commit ref is correct and non-fabricated regardless of whether verification runs from the main checkout or a linked worktree.
## [2026-07-05T18:15:46.597Z]
The audit that inventories active suppress markers must waive exactly what the reviewer waives — never more, never less — or it would either hide a live waiver or invent one that has no effect. For Markdown files, a marker inside a fenced code block is a documented example rather than a live waiver, so the audit now excludes fenced lines using the same fence detector the reviewer-honoring path uses. This required giving the raw-line audit scan the file path so it can recognize a Markdown file among other grammarless files, since only Markdown gets fence handling. Keeping both paths on one shared detector is deliberate: two separate implementations would drift, and a divergence here means the audit and the reviewer disagree about which waivers are real.
## [2026-07-10T08:10:35.938Z]
The suppression scan now flags a waiver that silences a rule labeled as only ever firing on provable violations. Such a rule has no false positives by design, so waiving one is almost always either a mislabel or a real problem worth re-examining. The warning is advisory and the inventory still reports cleanly; the set of such rules is supplied by the caller so this backend stays free of graph-policy decisions.
## [2026-07-10T12:40:56.304Z]
The suppression inventory now classifies a whole-file waiver — an unclosed disable marker whose position falls within the first five non-empty lines of a file — as "file-level", listing it under that label and no longer emitting the "Unbounded range" warning for it. That warning was meant to catch a disable marker whose closing enable was forgotten, but it fired on every unclosed disable, including the sanctioned top-of-file form used to intentionally exempt an entire file; the deliberate whole-file waiver and the accidental forgotten-close were indistinguishable. An unclosed disable placed lower in the file still warns, because there it usually is a forgotten close. The open-disable pairing that decides which disables are unclosed is reused to make this classification, keeping that pairing in a single place. The honored suppression line ranges are untouched — this changes only how the inventory labels a marker and whether it warns.
## [2026-07-10T14:39:30.529Z]
Added a read-only accessor that runs the dependency-resolution pass once and returns the full set of statically-detected cross-node code edges (source component to the set of components it depends on), verbatim and before any declared-versus-detected filtering. This exists so a caller that is not allowed to reach the dependency-resolution layer directly can still obtain the detected half of the structural dependency picture through this single read-only facade. It reuses the exact same pass invocation the boundary computation already performs, writes nothing, touches no verification state, and changes no verdict logic; on a genuine parse failure it returns nothing so the caller can fall back to declared relations only rather than fabricate edges.
